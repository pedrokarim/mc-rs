Architecture

6-crate workspace designed for modularity and clean separation of concerns.

Crate Dependency Diagram

The workspace is organized as a directed acyclic graph of crate dependencies. mc-rs-server sits at the top as the entry point, depending on all other crates.

Crate Details

mc-rs-server

The server entry point and main binary crate. Hosts the tokio async runtime, the ConnectionHandler state machine that manages each client's lifecycle, and the game tick loop running at 20 TPS (50ms intervals via tokio::select!). Handles world generation (flat and Perlin noise), multi-player broadcasts (AddPlayer, RemoveEntity, PlayerList), day/night cycle, weather cycle, player persistence (JSON files), and dispatches commands. Orchestrates all other crates.

mc-rs-proto

Implements ~30 Bedrock packet types with manual ProtoEncode/ProtoDecode implementations. Provides the VarInt/VarLong zigzag codec, VarUInt32/VarUInt64, zlib and snappy compression, and batch framing. Large payloads like biome definitions and entity identifiers are embedded via include_bytes!.

mc-rs-raknet

Full RakNet UDP transport implementation. Handles reliability layers (reliable, reliable-ordered, unreliable), packet fragmentation and reassembly, sequence/ordering channels, acknowledgments (ACK/NAK), congestion control, and MOTD formatting. This is the lowest-level network layer that sits between raw UDP sockets and the protocol codec.

mc-rs-crypto

Provides ECDH P-384 key exchange for the encryption handshake, AES-256-CTR stream cipher for ongoing packet encryption, and JWT parsing for validating Xbox Live authentication chains during login. Supports both online (Xbox Live) and offline authentication modes.

mc-rs-nbt

Implements the NBT (Named Binary Tag) serialization format in both little-endian (disk) and network (ZigZag VarInt) variants. Supports all tag types: compound, list, byte/int/long arrays, strings, and numeric types. Used by the protocol layer for block entity data, item NBT, and metadata blobs.

mc-rs-command

Command framework with 16 built-in commands and a CommandAction return system for side effects. Supports typed arguments (int, float, string, position), relative coordinates (~), and the CommandRegistry for sending the AvailableCommands packet enabling client-side tab completion. Commands: help, list, tp, gamemode, say, time, kill, stop, ping, seed, pos, difficulty, weather, spawn, up, clear.

Data Flow

Every packet follows a consistent pipeline through the server:

Inbound: Client → UDP Socket → RakNet (reassemble, order) → Decrypt (AES-256-CTR) → Decompress (zlib/snappy) → Batch Split → Packet Decode → ConnectionHandler
Outbound: ConnectionHandler → Packet Encode → Batch → Compress (zlib/snappy) → Encrypt (AES-256-CTR) → RakNet (fragment, reliability) → UDP Socket → Client

The ConnectionHandler is a state machine with well-defined states:

  1. SessionStart — Waiting for RequestNetworkSettings
  2. Login — JWT verification, identity extraction
  3. Encryption — ECDH key exchange, encryption negotiation
  4. ResourcePacks — Resource pack exchange (currently no packs sent)
  5. PreSpawn — StartGame, chunk loading, biome definitions, creative content
  6. InGame — Full gameplay (movement, chat, commands)

Each state only accepts its valid set of packet types. Any out-of-state packet is rejected, preventing protocol exploits.

Threading Model

MC-RS uses a single-task async model built on tokio:

  • Network I/O — A single tokio task handles all UDP socket reads/writes via the RakNet layer. Each client connection is a ConnectionHandler struct (not a separate task), processed cooperatively in the main loop.
  • Game Tick — The game world is ticked synchronously at 20 TPS (50ms intervals) using tokio::select! alongside packet processing. This avoids the complexity of cross-thread state synchronization.
  • No per-client tasks — All clients are handled within the same async loop. The server iterates over connections, processes incoming packets, and sends outgoing responses in each tick cycle.
  • Player persistence — Player data is saved to JSON files in the players/ directory on disconnect and at periodic intervals.
Design choice: The single-task model was chosen over per-connection tasks to avoid the complexity of synchronizing shared game state across threads. With 20 TPS and efficient packet batching, a single task comfortably handles multiple concurrent players.
